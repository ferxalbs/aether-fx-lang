# Reference performance and memory

The local reference preview meets the v0 target of frame p95 ≤ 41.67 ms at 720p. The latest visible run measured 1.90 ms for the complete player RAF callback that evaluates and draws a changed frame, with zero dropped frames during three complete 20-second plays. This is a measured result for the illustrated short on the host below, not a platform-wide performance promise.

## Reference and commands

Measured on 2026-10-10 in Lima (reports use UTC): iMac20,1, Intel Core i5-10400F 2.90 GHz, six physical/twelve logical cores, 24 GiB RAM, macOS 15.7.7 (Darwin 24.6.0), Node 24.21.0, Chromium 156.0.8078.4, Playwright 1.64.0, esbuild 0.28.2 and FFmpeg 8.0.1. Resolution is 1280×720, DPR 1. Sources, numeric samples, process traces, screenshots and codec stderr are retained in `artifacts/performance`.

Run the existing build before benchmarking changed package sources, then:

```sh
node scripts/benchmark-preview.mjs
node scripts/benchmark-export-memory.mjs
node scripts/benchmark-web-memory.mjs
node scripts/verify-bundle-budgets.mjs
```

The web memory benchmark consumes the verified repetition generated by the Node memory benchmark. Neither script modifies the original fixture or assets. Export evidence uses newly created directories and never overwrites an existing movie. The visible preview command opens a real browser window and runs three full plays at 1×; keep its document visible. It uses Playwright's documented `headless: false` option. [Playwright BrowserType](https://playwright.dev/docs/api/class-browsertype#browser-type-launch)

The current `preview-report.json` records:

Compilation has ten warmup iterations. First-frame and seek samples are separated by real animation frames. The cold startup's first Canvas drawing took 2.60 ms; navigation through resources/player readiness took 321.44 ms. Those are separate single observations and do not replace the warm p50/p95 measurements. Startup excludes the server's earlier compilation/build work.

All three plays delivered the 479 changed frames after frame zero plus the final pause drawing, with zero dropped frames. The measured player callbacks had maximum duration 2.10 ms; in-play RAF intervals had maximum 14.50 ms. Screenshots at the start and end were inspected. No repeated pixel readbacks alter Chromium's Canvas backing strategy during the benchmark.

The draw timing includes absolute evaluation and Canvas command submission. RAF cadence and dropped-frame counters provide complementary visible playback evidence. They do not measure the physical display's presentation timestamps or speaker latency: animation callbacks are part of the browser's rendering steps and rendering opportunities depend on hardware and scheduling. [HTML rendering processing model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model)

## Full pipeline memory and export

`ps` RSS is sampled every 250 ms for exports and 500 ms for preview. The local `ps(1)` manual defines RSS in 1024-byte units. Reports sum the benchmark coordinator and all its descendants, excluding the sampling process. Node export includes Chromium/GPU/renderers/network and FFmpeg; native web export includes those browser processes and the progressive file sink's coordinator. Shared pages may be counted more than once and sampling can miss short peaks. These numbers are aggregate process RSS, not unique physical memory.

| Backend at 720p | 20 s peak MiB | 60 s peak MiB | Export seconds, 20 / 60 | Export factor, 20 / 60 |
| --- | ---: | ---: | ---: | ---: |
| Reference Chromium → FFmpeg VP9/Opus | 1428.83 | 1496.28 | 14.46 / 37.58 | 0.723 / 0.626 |
| Native WebCodecs → progressive host file | 1560.31 | 1622.25 | 20.65 / 64.16 | 1.032 / 1.069 |

Export factor is elapsed export time divided by movie duration. The native measurement includes the Playwright binding that carries encoded packets to the host sink; it is not a measurement of encoding alone or a browser-local download sink.

The 60-second project resets each cycle to the original first snapshot and repeats the PCM data three times under a new asset version/hash. All 1440 draw-command states match the original modulo 480 before export. Both Node outputs decode exactly 480/1440 VP9 frames and 960000/2880000 audio samples. Both native outputs decode those frame counts and 960648/2880648 audio samples, preserving the separately documented 648-sample Opus tail. The existing FFmpeg Opus EOF diagnostic is retained in every report; exit codes and complete decoded counts are checked. See `node-export.md` and `browser-export.md` for codec padding and the earlier source investigation.

Three times the frames increased measured peak aggregate RSS by 4.72% for Node and 3.97% for native web export. This supports the bounded-frame result for this workload alongside direct ownership/queue evidence: Node captures and awaits one frame/write at a time; native producer/video capacities are one, audio capacity is four, and observed native encoder queues were one each. Native live VideoFrame/AudioData/encoder sets all end at zero, and tracked closed objects are deleted from the audit sets. The host sink has one active write and never accumulates the complete compressed file in a Blob.

All 22 observed Node-export Chromium/FFmpeg PIDs and all 20 observed native-export Chromium PIDs were absent from the live process table afterward, including any reparented process. Preview aggregate RSS peaks across its three passes were 1645.92, 1614.32 and 1613.28 MiB, settling after the first pass. The preview coordinator also contains compiler/bundle benchmark allocations; this is not an isolated FxPlayer heap figure. A bounded frame queue does not imply constant memory for arbitrary-duration assets: decoded audio and input bytes scale with their source duration.

The public `ExportReport.peakRssBytes` still measures only its Node coordinator. The separate process traces provide the full pipeline observation. There is no universal heap-leak claim, forced-GC measurement, physical mobile result or Firefox/WebKit 60-second memory claim.

## Bundle baseline and caps

Both visible runs produced identical minified ESM browser bundle sizes with default gzip compression. Each standalone entry bundles its transitive dependencies, so these totals overlap and must not be added to estimate a composed application.

| Standalone entry | JS bytes | Gzip bytes / recorded cap |
| --- | ---: | ---: |
| Core, all exports | 34661 | 10163 |
| Canvas player/renderer/resources | 20955 | 5758 |
| Compiler/parser, all exports | 148444 | 40920 |
| Browser export, all exports | 127928 | 35351 |

`bundle-budgets.json` records the first reviewed baseline as exact caps with no arbitrary headroom. `verify-bundle-budgets.mjs` builds and checks those caps, records the input graph, and rejects Node/Playwright imports in browser bundles and parser imports in core/player. The preview benchmark uses the same measurement helper. CI must invoke that command; preparing/enforcing the final workflow remains a separate release gate. A justified size increase requires review and an explicit baseline update.

Reference asset bytes are separate: Nunito TTF 276932, paper PNG 759, and original stereo PCM WAV 3840044. Their exact hashes remain in the preview report and fixture manifest. They are excluded from public npm tarballs. The existing runtime/peer dependency inventory is in `licensing.md`; the bundle input graphs record dependencies that survive tree shaking.
