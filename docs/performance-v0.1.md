# Candidate performance and reproducibility

The historical matrix and token/spike measurements belong to local 0.2.0-rc.1 sources and exact tools in the release manifest, on Darwin 24.6.0 x64 / i5-10400F / 24 GiB, Node 24.13.1. They do not qualify Linux, other hosts or physical devices. Node 22.12.0 also passed the 126 regression tests in that snapshot; hosted Node 22/24 acceptance is pending.

The final matrix compares two paths on identical source/assets and 24 fps: the retained Chromium/external-FFmpeg path and the historical native Skia/Mediabunny/NodeAV experiment (isolated from the default install). This is a backend comparison, not a newly executed performance baseline of the original historical commit. All 480 reference states remain equal to the v0 baseline. The 60-second workload repeats that animation and its full PCM audio three times, resetting the first-shot state. The current Skia/external-FFmpeg and Chromium/external-FFmpeg matrix is reproducible with `node scripts/benchmark-candidate.mjs <new-directory>` or `afx bench` with explicit dimensions/backend/repeat/output. The native experiment belongs to the previous RC.1 code and requires the explicit integrated entry and separately qualified optional peers.

Bench wall export time starts inside the exporter and excludes preceding CLI source/asset loading; `elapsedSeconds` additionally records the complete child/coordinator run. The export factor is exporter seconds / timeline seconds. Aggregate RSS sums the child exporter and descendants from external `ps` sampling every 250 ms, excluding the sampler and benchmark coordinator. Shared pages can be double-counted and sub-sample peaks missed. CPU is the maximum sampled cumulative process-tree total: a lower bound if children disappear between samples. `process.cpuUsage` records only the exporter Node process and its native threads, including integrated codec threads when that encoder is used. It excludes external FFmpeg/Chromium processes; their CPU requires process-tree sampling. No coordinator-only RSS is presented as total memory.

The matrix is sequential; no other acceptance/export jobs run simultaneously. It contains one run per cell, not a statistically established throughput distribution. These historical results retain their original source/tool scope; current acceptance reports and archive hashes are separate.

Native 20s/720p also takes 8.06s for the complete child/coordinator run (factor 0.403). It passes the host target of exporter factor <=0.5 and aggregate RSS <=700 MiB. Native 1080p exceeds both values; the target was specified at 720p, and scaling is not assumed. Rate-control/thread policies differ: native VP9 4 Mb/s with server defaults; oracle CRF30, cpu-used4, row-mt1, two threads. Outputs differ substantially in bytes, so this is not an equal-quality/causal comparison of Chromium removal alone.

Browser preview acceptance records expected/actual frame, RAF gaps, audio clock/resume/control/visibility and timeouts. Three current full 480-frame plays passed with zero dropped draws. Historical failures remain in artifacts; later green runs do not prove a repaired historical host/product cause.

Native raster parity uses eight frames from the actual renderer plus the same Canvas scene graph on skia-canvas 3.0.8, against pinned full Chromium. Predeclared tolerances: mean absolute channel error <=2, pixel fraction with any channel error >2 <=5%; maximum channel differences remain reported. This is approximate visual parity for that font/artwork, not pixel equality or multilingual shaping conformance. The isolated spike's RSS is coordinator-only with both libraries loaded, and is not a valid isolated-backend/process-tree memory comparison. Linux installation remains unmeasured.

Token comparison uses js-tiktoken 1.0.21 / cl100k_base and ten complete scene pairs, with exactly equal evaluated content across all 48 frames. Both omit equivalent defaults and use the same linear animation. v0 expands cubic contours/components; v0.1 uses primitives/time/reuse. Totals: 3362 versus 1358 tokens, a 59.6% reduction. Exact floating-point cubic coordinates are preserved. This is not live generation usage, a general tokenizer guarantee or a hand-rounded visual-equivalence claim. The full paired sources, conditions and hashes are in the historical token report. Use the matching baseline compiler/core bytes for reproduction; this is not a newly executed RC.2 token measurement.

Reproduce token measurement by installing js-tiktoken 1.0.21 and the two supplied baseline 0.1.0 archives in an isolated directory, then set `AFX_TOKENIZER_PATH` to its js-tiktoken/dist/index.js and `AFX_BASELINE_ROOT` to its node_modules/@aether-fx when running `node scripts/measure-tokens.mjs`. The old archive JS bytes were verified identical to the measured baseline. skia-canvas 3.0.8 is similarly an isolated optional measurement install; `AFX_SKIA_PATH` selects its lib/index.mjs for `scripts/spike-renderers.mjs`.

Fuzzing ran 100000 trials (37733 distinct texts), <=4096 bytes/input, four terminated workers, 128 MiB old-generation heap each and a 1-second per-input watchdog. It accepted 20828 and validly rejected 79172, with zero unexpected crashes or product timeouts; an independent intentional synchronous spin was terminated. The gzip JSONL corpus, seed/generator/corpus hashes, counters and empty unexpected-failure repro list are retained. These bounded results are not a universal no-hang proof.

Bundle budgets are unchanged and fail: core 10603/10163; canvas 6145/5758; compiler 46751/40920; export 53519/35351 gzip bytes. Easing, bounded syntax/diagnostics and MP4 muxing add bytes; official AAC WASM is an optional entry outside the default browser graph. Caps are not raised. These are historical RC.1 sizes; the current bundle report is authoritative for the new package graph.

The RC.2 WebM default graph separates MP4 muxing and optional AAC: export drops from 53519 to **35947 gzip bytes**, a 17572-byte reduction with the same esbuild measurement method. Current core/player/parser remain **10603 / 6145 / 46751**. Unchanged caps are **10163 / 5758 / 40920 / 35351** respectively, so all four gates still fail. The metafile attributes the remaining export size mainly to core validation/evaluation and WebM muxing/codec infrastructure; parser size includes core, bounded normalization/diagnostics and Chevrotain. Core/player contain no parser or Node/native codec imports. Keeping current semantic validation and implemented language behavior requires further optimization or an explicitly reviewed budget decision; no cap increase is applied here.

Current native parity was checked again against eight freshly rendered Chromium poses: maximum mean channel error 0.0874 and differing-pixel fraction 0.003956, within the declared 2/0.05 tolerances. Rerendered PNG bytes match on this host. This supports the renderer separation; it does not establish universal font/shaping or cross-platform pixel equality. Historical integrated and Chromium export figures above use different codec policies and must not be interpreted as a renderer-only speed comparison.

On Node 24.21.0 / Darwin 24.6.0 x64, the provisional Skia + external FFmpeg 8.0.1 path was measured at 20 s/1280×720/24 fps using the reference scene/audio. VP9 CRF30, deadline good, cpu-used4, row-mt1 and two threads are identical across the transport comparison. PNG transport took **19.167 s**, factor **0.958**, aggregate RSS **478.3 MiB**, sampled process-tree CPU **41.86 s**. Raw RGBA transport took **11.474 s**, factor **0.574**, aggregate RSS **551.1 MiB**, sampled CPU **31.00 s**. These are single sequential observations after acceptance jobs ended, sampled every 250 ms; shared-page counting and missed peaks/CPU from exited processes remain limitations. Raw transport removes unnecessary PNG encode/decode; no renderer or video quality policy changed. Memory passes the 700 MiB target; speed fails the 0.5 target. No threshold or encoding-quality change is used to turn this into PASS. These figures must not be compared causally with the historical integrated encoder's different rate-control policy.

## RC.3 affected gates

RC.2 runtime bytes were reproduced on base 1a79d29 (repository guidelines added after 8f8bc09): core/player/compiler/export 10603/6145/46751/35947 gzip bytes; the unchanged native benchmark took 11.489 s, factor 0.57446, tree RSS 553.1 MiB and sampled CPU 31.07 s. Tools: Node 24.21.0, esbuild 0.28.2, @napi-rs/canvas 1.0.11, FFmpeg 8.0.1, Darwin 24.6.0 x64, i5-10400F / 24 GiB.

Final standalone bundles remain fully bundled, minified ES2022 ESM with Node default gzip; no dependencies are excluded and no additional chunks exist. Internal ESM boundaries remove schema initialization from Player. Repeated immutable schema rules are interned during build; a structural equality check covers every original rule and the public JSON schema stays byte-identical. Syntax minification preserves APIs, types and source maps.

The consumer metafiles retain the full import graph and per-module contributions. Compiler's largest cost is Chevrotain: approximately 108 KB of minified output including its regexp/GAST utilities, versus 26 KB of compiler code and 25 KB of reachable core. Parser construction pulls grammar analysis, recognition/recovery and lexer machinery through dynamic prototype composition; removing those pieces is not ordinary unused-import elimination. Core retains validation, evaluation and patch contracts; export retains validation and WebM muxing. Caps are unchanged; these three failures remain gates rather than an approved budget increase.

The profile measured 0.663 s evaluation, 0.479 s Skia draw, 0.928 s RGBA read, 0.342 s RGBA copy, 7.926 s pipe wait and 1.030 s finalization before optimization. The final profile has 0.639/0.433/0.927 s evaluation/draw/read, no extra RGBA copy, 8.007 s pipe wait and 1.016 s finalization; FFmpeg process lifetime is 11.050 s within the 11.096 s exporter total. Encoding overlaps producer work and pipe waits: these timings must not be added as independent stages. A bounded next-frame prefetch experiment did not demonstrate a useful total-time gain and was removed. The delivered path remains sequential, one pending pipe write, and independently owned image-data storage kept alive through its callback.

Three consecutive runs used the exact reference scene/audio, 1280×720, 24 fps, 480 frames, VP9 CRF30 / deadline good / cpu-used4 / row-mt1 / threads2, Opus 128 kb/s, without concurrent heavy jobs. Each output receives independent audiovisual decode.

## Bounded follow-up to RC.3

RC.3 remains an immutable candidate, including its acceptance and three benchmark runs. The follow-up changes the build-time schema counter: children of a shared subtree are counted once, preventing single-use aliases. The original schema remains structurally equal, with unchanged public JSON, diagnostics and APIs. Core/Player/Compiler/Export now measure **10455 / 4339 / 46534 / 35764 gzip bytes** under the same gate. Savings are 13 / 0 / 15 / 13 bytes; Core still exceeds its cap by 292 bytes, Compiler by 5614 and Export by 413. No new candidate is packaged for these residual failures. Counting more short rules and sharing serializers/encoder close helpers were measured and rejected because they worsened or did not improve gzip.

RC.3's minified module attribution is Core schema 11103, validation 8516, evaluation 3815, patch 2352, compilation/serialization 2221 and remaining geometry/time/types 2801 bytes. Export includes 86604 bytes of Mediabunny, 28239 of core and 8813 of export/canvas. No accidental parser, Node, integrated encoder, MP4 muxer or AAC WASM is reachable in the default browser export. The 305/426-byte gzip excesses are whole-bundle differences, not additive module costs. Sharing schema descendants accounts for the measured 13-byte reductions in both bundles; the remaining costs retain implemented contracts.

Compiler's RC.3 output is 160216 minified bytes: **108398 Chevrotain family, 26353 compiler, 25322 core**, plus 143 bytes of bundler syntax/exports. Only the public `chevrotain` entry is imported. Bundling its four used exports alone (`createToken`, `EmbeddedActionsParser`, `Lexer`, `EOF`) yields 108403 minified / 29633 gzip bytes. Standalone gzip is not an additive attribution to the full compiler. Unused diagram/CST declaration generation contributes no output; dynamic prototype composition keeps parser traits, including recovery/tree building, accessible. `skipValidations` is a runtime option and does not remove those imports; disabling validation or changing existing recovery behavior is outside this optimization. There is no demonstrated supported-import saving sufficient for the remaining 5614 bytes. A structural parser/capability or budget decision remains pending; these measurements do not prove that a parser replacement is necessary, or that further tree shaking will meet the cap. See [Chevrotain grammar validation](https://chevrotain.io/docs/guide/resolving_grammar_errors.html) and the installed 13.2.0 parser/mixin sources.

The profiler now records the actual production FFmpeg arguments. Add `--ffmpeg-verbose` to capture filter negotiation; that mode is diagnostic, not a comparable benchmark. FFmpeg 8.0.1 / libvpx 1.15.2 confirms raw RGBA 1280×720 at 24/1, one same-size RGBA → YUV420p conversion, VP9 CRF30, deadline good, cpu-used4, row-mt1, output codec threads2, and Opus 128 kb/s. Reference audio uses sample trim 0–960000, timestamp reset, gain1, delay0 and padding to 960000 samples. Audio negotiation converts s16 → fltp → flt without resampling; the general filters implement trim/gain/offset/padding for other plans. There is no PNG encode/decode or repeated video conversion. Two codec threads are an explicit existing benchmark policy, not a newly discovered automatic limit. Changing threads, preset, rate control or hardware requires a separately measured configuration comparison; no such change is delivered. [FFmpeg option scope and pipeline](https://ffmpeg.org/ffmpeg.html) explain input/output option placement.

The diagnostic profile records 0.692 s evaluation, 0.450 s drawing, 0.969 s RGBA read, 8.255 s pipe wait, 1.015 s finalization and 11.410 s overlapping FFmpeg lifetime. It supports the existing bottleneck attribution, not a new throughput improvement or process-tree memory measurement. Independent decode passes 480 frames, 20 s, audio sample counts and synchronization within one frame. Build, types and 128 regression tests pass. Full acceptance was not rerun and no RC.4 was made for a 13-byte build optimization that leaves mandatory gates failed. Linux remains unverified: no local Linux runtime is available; the existing Ubuntu Node 22/24 workflow needs these changes on an authorized remote ref before CI can qualify them.

## Proposed v0.2 bundle policy — not applied

The enforced caps remain 10163/5758/40920/35351 gzip bytes; Core/Compiler/Export FAIL at 10455/46534/35764 and Player passes at4339. Those caps are the twice-observed original baseline, not derived user load-time limits. A future v0.2 policy could retain every import-isolation check and the exact measurement method, while adopting measured current scope plus a nominal 10% growth reserve rounded upward to256 bytes:

| Bundle | Current measured gzip B | Proposed cap B | Growth reserve B |
| --- | ---: | ---: | ---: |
| Core | 10455 | 11520 | 1065 |
| Player | 4339 | 4864 | 525 |
| Compiler | 46534 | 51200 | 4666 |
| Export | 35764 | 39424 | 3660 |

This is an explicit policy proposal for one minor-release cycle, not an empirically proven UX requirement or automatic baseline update. It accommodates the implemented bounded authoring/diagnostic contracts and supported Chevrotain machinery without replacing the parser or hiding dependencies. The reserve is a review trigger for future changes, not a target to consume. The largest standalone proposal transfers about0.410s of payload at1Mbit/s before protocol latency or parse/execute costs; bundles overlap and must not be summed as application size. Approval should require representative cold-load/parse measurements on a declared browser/device/network and no unintended import growth. Without that decision, the current size gates continue failing and release remains unapproved.

No new speed threshold is proposed. The existing three macOS observations still fail10s/factor0.5 and pass700MiB. Production latency/concurrency and a declared reference Linux host must be established before any separate performance-policy review. Hosted Ubuntu observations are platform qualification evidence, not directly comparable reference timings. See [Linux validation preparation](linux-validation.md).
